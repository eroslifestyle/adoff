Blocage des publicités par le SDK IMA, expliqué

Le SDK IMA de Google est la bibliothèque utilisée par les lecteurs vidéo pour demander et diffuser des publicités. Le bloquer au niveau réseau fait tomber les lecteurs, aussi AdOff le remplace-t-il par une version factice qui répond à chaque demande de publicité par un événement immédiat « reprendre la lecture du contenu » : le lecteur fonctionne, mais les publicités ne s’affichent jamais.

Ce qu’est réellement le SDK IMA

Le SDK Interactive Media Ads (IMA) est la bibliothèque côté client de Google dédiée à la publicité vidéo. Un site web souhaitant monétiser une vidéo ne construit généralement pas son propre lecteur publicitaire : il charge imasdk.googleapis.com/js/sdkloader/ima3.js (ou la variante dynamique ima3_dai.js), initialise un AdDisplayContainer, et transmet au SDK une URL de balise publicitaire. Le SDK récupère ensuite une réponse VAST, affiche la publicité à l’intérieur du lecteur, suit les impressions et les quartiles, puis restitue le contrôle au contenu éditorial du éditeur.

Parce qu’il s’agit d’un seul et même script partagé servi depuis un seul et même domaine, le SDK IMA constitue le point de blocage le plus stratégique dans la publicité vidéo web : le neutraliser une seule fois suffit à faire cesser la diffusion d’annonces pour tous les lecteurs qui l’utilisent.

Le cycle de vie d’une demande d’annonce

Lorsqu’un spectateur appuie sur lecture, le lecteur exécute généralement cette séquence :

  1. La page charge ima3.js à partir des serveurs de Google.
  2. Le lecteur crée un chargeur de publicités et demande des publicités via une balise publicitaire pointant vers un serveur de publicités.
  3. Le SDK récupère la publicité (généralement un document VAST/VMAP via DoubleClick), l’analyse, puis affiche le contenu publicitaire dans un conteneur superposé à la vidéo.
  4. Les pixels de suivi sont déclenchés ; le lecteur attend.
  5. Lorsque la publicité se termine (ou génère une erreur), le SDK déclenche CONTENT_RESUME_REQUESTED, et le lecteur reprend la vidéo principale.

Cet événement dernier est crucial : le lecteur est programmé pour attendre qu’il se produise. Celui qui contrôle le SDK contrôle le moment où le contenu reprend.

Pourquoi bloquer simplement le SDK fait planter les lecteurs

La méthode brute consiste à bloquer imasdk.googleapis.com au niveau réseau et à s’arrêter là. Le problème : de nombreux lecteurs interprètent un échec ou une absence de SDK comme une erreur fatale et refusent de lancer la vidéo, affichant au lieu du contenu une roue de chargement ou un mur « bloqueur de publicités détecté ».

C’est pourquoi les bloqueurs classiques au niveau réseau sont inefficaces face aux publicités vidéo : ils peuvent bloquer la requête publicitaire, mais ils ne peuvent pas répondre à la question du lecteur « Puis-je reprendre maintenant ? ». Seul un composant agissant à la place du SDK peut le faire.

Neutralisation par substitution : l’approche « stub »

AdOff emprunte une voie différente : au lieu de bloquer le SDK, il le remplace. Un stub qui imite l’API publique du SDK IMA est inséré à sa place, de sorte que le lecteur « voit » toujours un SDK fonctionnel — un SDK qui se comporte comme si chaque interruption publicitaire était vide.

Lorsque le lecteur appelle adsManager.start(), le stub émet immédiatement CONTENT_RESUME_REQUESTED. Le lecteur reprend le contenu instantanément. Aucune publicité n’est récupérée, aucune publicité n’est rendue, et le lecteur n’entre jamais dans un état d’erreur, car il ne remarque rien de manquant.

Deux canaux de livraison pour le même stub

AdOff envoie le même stub via deux canaux, car les différents sites chargent le SDK de manière différente :

  • Injection dans la page. Sur les sites non exclus, un script du monde principal définit window.google.ima avant l’initialisation du lecteur, de sorte que le SDK intégré ou chargé externement est remplacé par le stub.
  • Redirection réseau. Pour un ensemble de 42 domaines de diffuseurs européens, les règles declarativeNetRequest redirigent la requête vers ima3.js et ima3_dai.js vers le fichier stub intégré dans l’extension. La page charge ce qu’elle croit être le SDK de Google, mais obtient en réalité celui d’AdOff.

Ces deux canaux aboutissent au même résultat : le joueur obtient un SDK réactif, et le spectateur obtient du contenu.

Où cette approche fonctionne et où elle ne s’applique pas

Le stub neutralise la publicité basée sur IMA côté client. Il n’a aucun effet sur l’insertion serveur de publicité (SSAI), où les publicités sont intégrées directement dans le flux vidéo avant sa diffusion — il n’y a alors aucun appel SDK à intercepter. Les services d’abonnement premium utilisant leurs propres pipelines publicitaires sont délibérément exclus afin que leurs lecteurs continuent à fonctionner.

La principale plateforme vidéo bénéficie également d’un pipeline dédié en plus : la programmation des publicités est supprimée de la réponse du lecteur avant que la page ne la lise, et tout ce qui échappe à cette suppression est avancé rapidement.

Pourquoi cela compte pour l’avenir du blocage d’annonces

Les plateformes publicitaires transfèrent progressivement la charge vers les SDK côté client précisément parce que les bloqueurs naïfs peinent à les gérer. Une approche qui répond au lecteur plutôt que de le priver de contenu est robuste : elle ne dépend pas de l’énumération de chaque URL publicitaire, mais uniquement du contrat propre au SDK selon lequel le contenu doit reprendre.

Questions fréquentes

Bloquer le SDK IMA revient-il à le remplacer ?

Non. Le bloquer au niveau réseau empêche souvent la lecture de la vidéo, car les lecteurs attendent que le SDK signale que le contenu peut reprendre. Le remplacer par un stub permet de garder le lecteur entièrement fonctionnel tout en garantissant qu’aucune publicité n’est jamais demandée.

Que se passe-t-il lorsque l’« stub » reçoit une demande d’annonce ?

Le stub expose la même surface d’API que les lecteurs attendent. Lorsqu’on lui demande de lancer les publicités, il déclenche immédiatement l’événement de reprise du contenu, afin que la lecture se poursuive sans aucune publicité ne soit récupérée ni affichée.

Un « stub » IMA fonctionne-t-il avec l’insertion d’annonces côté serveur ?

Non. Avec SSAI, les publicités sont intégrées dans le flux vidéo côté serveur avant la diffusion, donc aucune appel au SDK côté client n’est à intercepter. L’insertion côté serveur nécessite des contre-mesures différentes et dépasse le cadre d’une extension de navigateur.

Quels navigateurs peuvent exécuter ce type d’extension ?

AdOff est construit sur Manifest V3 et fonctionne sur Chrome, Firefox, Safari, Edge et Opera. La couche de neutralisation IMA est incluse dans la version gratuite, sans compte ni inscription requis.

Un site peut-il détecter que le SDK a été remplacé ?

C’est précisément le rôle de la couche furtive : le spoofing de pièges et l’interception de fetch/XHR donnent l’impression à des scripts anti-blocage de publicités que l’environnement est ordinaire. Aucune méthode n’est permanente, car les plateformes modifient fréquemment leurs mécanismes de détection.
