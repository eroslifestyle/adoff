IMA SDK-Anzeigeblockierung, erklärt

Das Google IMA SDK ist die Bibliothek, die Videoplayer zum Anfordern und Abspielen von Werbung verwenden. Wenn es auf Netzwerkebene blockiert wird, funktionieren die Player nicht mehr. AdOff ersetzt es daher durch einen Stub, der jede Werbeanfrage sofort mit einem „Inhalt fortsetzen“-Ereignis beantwortet: Der Player funktioniert, die Werbung wird jedoch niemals geladen.

Was die IMA-SDK tatsächlich ist

Das Interactive Media Ads (IMA) SDK ist Googles clientseitige Bibliothek für Video-Werbung. Eine Website, die ein Video monetarisieren möchte, erstellt normalerweise nicht ihren eigenen Werbe-Player: Sie lädt stattdessen imasdk.googleapis.com/js/sdkloader/ima3.js (oder die dynamische Variante ima3_dai.js), initialisiert einen AdDisplayContainer und übergibt dem SDK eine Ad-Tag-URL. Anschließend ruft das SDK eine VAST-Antwort ab, rendert die Werbung innerhalb des Players, verfolgt Impressionen und Quartile und gibt schließlich die Steuerung wieder an den Inhaltsherausgeber zurück.

Weil es sich um ein gemeinsames Skript handelt, das von einer einzigen Domain aus bereitgestellt wird, stellt das IMA SDK den entscheidenden Engpass im Web-Video-Werbebereich dar: Sobald man es neutralisiert, stoppt jeder darauf basierende Player die Auslieferung von Werbung.

Der Lebenszyklus einer Anzeigenanfrage

Wenn ein Zuschauer auf „Wiedergabe“ klickt, führt der Player in der Regel folgende Sequenz aus:

  1. Die Seite lädt ima3.js von Googles Servern.
  2. Der Player erstellt einen Anzeigen-Loader und fordert Anzeigen mit einem Anzeigetag an, der auf einen Anzeigeserver verweist.
  3. Das SDK ruft die Anzeige ab (in der Regel ein VAST-/VMAP-Dokument über DoubleClick), parst sie und rendert das Anzeigemedium in einem Container über dem Video.
  4. Tracking-Pixel werden ausgelöst; der Player wartet.
  5. Sobald die Anzeige beendet ist (oder ein Fehler auftritt), löst das SDK CONTENT_RESUME_REQUESTED aus, und der Player setzt das eigentliche Video fort.

Das letzte Ereignis ist entscheidend: Der Spieler ist so programmiert, dass er auf dieses wartet. Wer die SDK kontrolliert, kontrolliert auch, wann der Inhalt fortgesetzt wird.

Warum das bloße Blockieren der SDK die Player zerstört

Der grobe Ansatz besteht darin, imasdk.googleapis.com auf Netzwerkebene zu blockieren und damit abzuschließen. Das Problem: Viele Player interpretieren ein fehlgeschlagenes oder fehlendes SDK als schwerwiegenden Fehler und verweigern den Start des Videos vollständig, wodurch stattdessen ein Lade-Spinner oder eine „Adblock erkannt“-Sperrmaske angezeigt wird.

Darum sind klassische Blocker auf Netzwerkebene gegen Videoanzeigen schwach: Sie können die Anzeigenanfrage blockieren, aber nicht die Frage des Players beantworten: „Kann ich jetzt fortsetzen?“. Nur etwas, das stellvertretend für das SDK agiert, kann das.

Neutralisierung durch Substitution: Der Stub-Ansatz

AdOff wählt einen anderen Weg: Anstatt das SDK zu blockieren, ersetzt es dieses direkt. Ein Stub, der die öffentliche API des IMA SDK nachbildet, wird eingefügt, sodass der Player weiterhin ein funktionierendes SDK „sieht“ – eines, das so tut, als wären alle Werbeunterbrechungen leer.

Wenn der Player adsManager.start() aufruft, sendet der Stub sofort CONTENT_RESUME_REQUESTED. Der Player setzt den Inhalt sofort fort. Es wird kein Werbevideo abgerufen, kein Werbevideo wiedergegeben, und der Player gelangt niemals in einen Fehlerzustand, da er nichts Fehlendes bemerkt.

Zwei Übertragungskanäle für denselben Stub

AdOff sendet denselben Stub über zwei Kanäle, da verschiedene Websites das SDK unterschiedlich laden:

  • In-Page-Injektion. Auf Seiten, die nicht ausgeschlossen sind, definiert ein Skript im Hauptkontext window.google.ima, bevor der Player initialisiert wird, sodass das eingebettete oder extern geladene SDK durch den Stub ersetzt wird.
  • Netzwerkumleitung. Für eine Gruppe von 42 europäischen Rundfunkanbieter-Domains leiten Regeln von declarativeNetRequest die Anfrage nach ima3.js und ima3_dai.js auf die im Erweiterungspaket enthaltene Stub-Datei um. Die Seite lädt, was sie für das Google-SDK hält, erhält aber stattdessen das von AdOff.

Beide Kanäle führen zum gleichen Ergebnis: Der Spieler erhält ein reaktionsfähiges SDK, der Zuschauer erhält Inhalte.

Wo dieser Ansatz greift – und wo nicht

Der Stub neutralisiert clientseitige, IMA-basierte Werbung. Er hat keinen Einfluss auf serverseitige Werbeeinblendung (SSAI), bei der Werbung bereits vor der Auslieferung direkt in den Video-Stream eingefügt wird – es findet hierfür kein SDK-Aufruf statt. Premium-Abonnementservices, die eigene Werbe-Pipelines nutzen, sind bewusst ausgeschlossen, damit ihre Player weiterhin funktionieren.

Die Haupt-Videoplattform erhält zudem eine eigene Pipeline: Die Werbeplanung wird aus der Antwort des Players entfernt, bevor die Seite sie liest, und alles, was dennoch durchschlüpft, wird vorgespult.

Warum dies für die Zukunft des Werbeblockings relevant ist

Werbeplattformen verlagern das Gewicht zunehmend auf clientseitige SDKs, precisely weil naive Blocker damit Schwierigkeiten haben. Ein Ansatz, der den Spieler beantwortet, anstatt ihn zu verhungern, ist robust: Er hängt nicht davon ab, jede Werbe-URL aufzulisten, sondern nur davon, dass der SDK-eigene Vertrag vorsieht, dass der Inhalt fortgesetzt werden muss.

Häufige Fragen

Ist das Blockieren des IMA SDK dasselbe wie dessen Ersetzung?

Nein. Das Blockieren auf Netzwerkebene verhindert oft die Wiedergabe des Videos, da die Player darauf warten, dass das SDK signalisiert, dass die Wiedergabe fortgesetzt werden kann. Durch die Ersetzung durch einen Stub bleibt der Player voll funktionsfähig, während sichergestellt ist, dass niemals Werbung angefordert wird.

Was geschieht, wenn der Stub eine Anzeigeanfrage erhält?

Der Stub bietet dieselbe API-Oberfläche, die die Player erwarten. Bei Aufforderung zur Werbung wird sofort das Content-Resume-Ereignis ausgelöst, sodass die Wiedergabe ohne Abruf oder Darstellung einer Werbung fortgesetzt wird.

Funktioniert ein IMA-Stub auch gegen Server-Side-Ad-Insertion?

Nein. Bei SSAI (Server-Side Ad Insertion) werden die Werbeinhalte bereits serverseitig in den Videostream eingefügt, bevor dieser ausgeliefert wird; daher gibt es keinen clientseitigen SDK-Aufruf, den abfangen könnte. Die serverseitige Einblendung erfordert andere Gegenmaßnahmen und liegt außerhalb des Wirkungsbereichs einer Browser-Erweiterung.

Welche Browser können diese Art von Erweiterung ausführen?

AdOff basiert auf Manifest V3 und funktioniert auf Chrome, Firefox, Safari, Edge und Opera. Die IMA-Neutralisierungsschicht ist in der kostenlosen Version enthalten, ohne dass ein Konto oder eine Registrierung erforderlich ist.

Kann eine Website erkennen, dass das SDK ersetzt wurde?

Das ist genau der Zweck der Stealth-Schicht: Spoofing von Lockvorgängen sowie Fetch/XHR-Abfangung lassen die Umgebung für Anti-Adblock-Skripte gewöhnlich erscheinen. Keine Methode ist dauerhaft wirksam, da Plattformen ihre Erkennungsmechanismen häufig ändern.
